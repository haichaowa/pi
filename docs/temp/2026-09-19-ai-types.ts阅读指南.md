# packages/ai/src/types.ts 阅读指南

> 2026-09-19 · 该文件是 pi 统一 AI 层的核心类型定义（882 行），定义了跨 provider 的请求/响应/流式数据模型。
> 建议按下面的顺序读，Compat 系列接口先跳过。

## 一、推荐阅读顺序与重点

### 1. 数据模型（最核心，先读）
- `Context`（L524-528）：一次请求的全部输入 = systemPrompt + messages + tools。极简，但是整个系统的"请求体"。
- `Message` 联合类型（L470）：`UserMessage | AssistantMessage | ToolResultMessage`。
  - 这是 TS 的 **discriminated union**（可辨识联合），类似 Java 的 sealed interface + 各实现类，或 Go 里带 type tag 的 struct。每个成员用 `role` 字段区分。
- 内容块类型（L351-381）：
  - `TextContent` / `ThinkingContent` / `ImageContent` / `ToolCall`
  - `AssistantMessage.content` 是这些块的数组（L430）——注意不是纯字符串， thinking/工具调用都是内容块。
  - `ThinkingContent.thinkingSignature`（L360）：provider 的签名/加密回放数据，多轮对话时原样传回。
- `Usage`（L383-404）：token 计量。注意 `reasoning` 是 `output` 的子集，不是叠加；`cost` 内嵌在 Usage 里。
- `StopReason`（L406）：`"pending" | "stop" | "length" | "toolUse" | "error" | "aborted" | "deferred"` —— agent 循环靠它决定是否执行工具、是否继续。

### 2. 流式事件协议（第二核心）
- `AssistantMessageEvent`（L546-562）：stream 期间发出的事件联合，`start → text_start/text_delta/text_end → ... → done | error`。
- 重点读 L530-545 的注释：`partial` 是"当前累积到哪了"的共享对象，不是快照；块在 `*_start` 时为空，靠 `*_delta` 增长，`*_end` 才是权威值。
- 这是理解 `AssistantMessageEventStream`（真正实现在 `utils/event-stream.ts`）的钥匙。

### 3. 请求选项体系（分层继承）
- `ProviderRequestOptions`（L124-177）：所有 provider 共享的底层选项——AbortSignal、可注入的 fetch、env 覆盖、`onPayload`/`onResponse` 钩子、headers、timeout/retry。
  - L152-158 的注释值得看：Bedrock 上自定义 header 要走 SigV4 签名中间件，保留头会被静默忽略——兼容性细节的典型样本。
- `StreamOptions extends ProviderRequestOptions`（L179-223）：加上 temperature、`samplingParams`（L186-193，给 llama.cpp/vLLM 等自建服务透传任意采样参数的逃生舱）、transport、cacheRetention、sessionId。
- `SimpleStreamOptions extends StreamOptions`（L314-322）：再加 `reasoning`、`deferred`、`thinkingBudgets`。日常用 `streamSimple()` 走这层。

### 4. 分发与类型魔法（TS 进阶，值得学）
- `Api = KnownApi | (string & {})`（L29）：**经典 TS 技巧**——`(string & {})` 保留已知字面量的自动补全，又允许任意字符串。provider ID 同理（L76）。
- `ApiOptionsMap`（L243-254）：KnownApi → 各 API 专属选项类型的映射表。注释指出 type-only import 在编译后会被擦除，所以 tree-shaking 安全。
- `ApiStreamOptions<TApi>`（L260-262）：**条件类型**（`TApi extends keyof ApiOptionsMap ? ApiOptionsMap[TApi] : ...`），类似 Java 泛型里的重载分发，但发生在类型层。
- `ProviderStreams`（L272-281）：每个 `src/api/` 模块的统一契约——必须导出 `stream` / `streamSimple`，可选 deferred 系列。这就是"插件接口"。
- `StreamFunction`（L324-337）：注意其契约注释——同步抛错只在缺鉴权时发生；流一旦建立，错误必须编码成 `stopReason: "error"` 的消息从流里发出。

### 5. Model 描述符
- `Model<TApi>`（L845-874）：统一模型元数据——id/api/provider/baseUrl/reasoning/输入模态/费用/上下文窗口。
  - `compat` 字段（L865-873）用嵌套条件类型按 API 选择对应 Compat 接口，和 `ApiStreamOptions` 同一手法。
- `ModelCost` / `ModelCostTier`（L827-842）：按 input token 量分档计价。

### 6. 可以后跳过的
- `OpenAICompletionsCompat`（L568-643）、`OpenAIResponsesCompat`、`AnthropicMessagesCompat`、`BedrockCompat`：各大 API 的兼容性开关清单，量大且是"查表用"的，遇到具体 provider 问题再回来查。
- `OpenRouterRouting`（L746-813）/ `VercelGatewayRouting`：网关路由参数，纯透传，用到再看。
- `DeferredHandle`（L410-420）及 deferred 相关：异步延迟响应机制，比较小众。
- Images 系列（`ImagesModel`/`ImagesContext`/`AssistantImages`）：图像生成管线，结构与文本侧对称，了解存在即可。

## 二、给 Go/Java/Python 背景的 TS 语法对照

| types.ts 里的写法 | 行号 | 对照理解 |
|---|---|---|
| `type A = "x" \| "y" \| (string & {})` | L29 | 枚举 + 允许扩展值；`(string & {})` 是为了保住 IDE 补全 |
| `interface X extends Y` | L179 | 同 Java/TS 继承，结构化而非名义化（duck typing 的接口） |
| discriminated union（`role`/`type` 字段区分） | L470, L546 | Java sealed interface + pattern matching；Go 的 type switch |
| `T extends U ? A : B`（条件类型） | L260, L865 | 类型层面的三元表达式/泛型分发 |
| `Record<string, string>` | L113 | 近似 `map[string]string` / `Map<String,String>` |
| `Partial<Record<K, V>>` | L85 | 所有键可选的 map |
| `Extract<StopReason, "aborted" \| "error">` | L562 | 从联合类型里筛选子集 |
| `Omit<Model, "api" \| ...>` | L877 | 基于已有类型去掉几个字段的"改造"（类似 Go 里内嵌再遮蔽） |

## 三、一句话总结

这个文件 = **统一数据模型（Message/Usage/StopReason）+ 流式协议（AssistantMessageEvent）+ 三层请求选项 + 按 API 分发的类型系统（ApiOptionsMap/条件类型）+ Model 元数据**；Compat 系列是各 provider 的兼容性开关表，按需查阅。
