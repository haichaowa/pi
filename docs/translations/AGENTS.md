# 开发规则

## 对话风格

- 回答保持简短精炼
- commit、issue、PR 评论和代码中不要使用 emoji
- 不要客套话或凑字的寒暄（例如写 "Thanks @user"，而不是 "Thanks so much @user!"）
- 只写技术性文字，直截了当
- 用语简洁、清晰、朴素。不得不用术语时，先用一句话定义。
- 解释非平凡的设计和问题时，按这个顺序来：先讲问题，再给具体示例或简短的执行轨迹，最后是解决方案。要说明为什么必须用这个方案，并把它与可选的复杂度区分开。
- 优先用具体行为和小例子来说明，而不是抽象总结、堆砌术语，或罗列一堆不加解释的改动。
- 用户提问时，先回答问题，再去改代码或执行实施类命令。
- 回应用户反馈或某项分析时，先明确说你同意还是不同意，再说你改了什么。

## 代码质量

- 在做大规模改动之前、在编辑尚未完整查看过的文件之前，以及在被要求调查或审计时，都要先完整读文件。大范围改动不要只依赖搜索到的片段。
- 除非万不得已，不要用 `any`。
- 只有一个调用点的单行 helper 直接内联。
- 外部 API 的类型去 node_modules 里查，不要猜。
- **禁止内联 import**（`await import()`、`import("pkg").Type`、动态类型 import），只允许顶层 import。
- 不要为了消除过时依赖导致的类型错误而删除或降级代码；正确做法是升级依赖。
- 在根配置检查范围内的代码（`packages/*/src`、`packages/*/test`、`packages/coding-agent/examples`）中只使用可擦除的 TypeScript 语法（Node strip-only 模式）：不要用参数属性、`enum`、`namespace`/`module`、`import =`、`export =` 或其他需要 JS emit 的构造。用显式字段加构造函数赋值来替代。
- 删除看起来是有意为之的功能或代码之前，一定要先问。
- 除非用户要求，否则不要保持向后兼容。
- 不要硬编码按键判断（例如 `matchesKey(keyData, "ctrl+x")`）。把默认值加到 `DEFAULT_EDITOR_KEYBINDINGS` 或 `DEFAULT_APP_KEYBINDINGS` 里，保持可配置。
- 永远不要直接修改 `packages/ai/src/models.generated.ts`；先更新 `packages/ai/scripts/generate-models.ts`，再重新生成。生成所产生的 `models.generated.ts` diff 总是可以一并提交，即使重新生成带来了无关的上游模型元数据变更也没关系。

## 命令

- 改完代码（非文档）后：运行 `npm run check`（看完整输出，不要只看末尾）。提交前修复所有 error、warning 和 info。该命令不运行测试。
- 除非用户要求，永远不要运行 `npm run build` 或 `npm test`。
- 永远不要直接跑完整的 vitest 套件：其中包含的 e2e 测试在存在 endpoint/auth 相关环境变量时会被激活。所有非 e2e 测试都在仓库根目录运行 `./test.sh`；否则在对应包的根目录运行指定的测试：
  - Vitest：`node "$(git rev-parse --show-toplevel)/node_modules/vitest/dist/cli.js" --run test/specific.test.ts`
  - `packages/tui`（`node:test`）：`node --test test/specific.test.ts`
- 创建或修改了测试文件，就要运行它，并不断调整测试或实现直到通过。
- `packages/coding-agent/test/suite/` 要用 `test/suite/harness.ts` 加 faux provider。不要用真实的 provider API、密钥或付费 token。
- 写回归测试修复 GitHub issue 时，在测试旁边加一条注释，标明 GitHub issue 编号。
- 临时脚本要 `write` 到临时文件（如 `/tmp`），运行，必要时编辑，用完删除。不要把多行脚本直接嵌在 `bash` 命令里。
- 除非用户要求，否则不要 commit。

## 依赖与安装安全

- 把 npm 依赖和 lockfile 变更当作经过评审的代码。直接外部依赖保持锁定精确版本。
- 更新 `undici` 时，必须先阅读目标版本的 changelog/release notes，评估其中的变更是否可能影响功能，然后再执行更新。
- 本地安装/更新依赖用 `npm install --ignore-scripts`；干净/CI 式安装用 `npm ci --ignore-scripts`。除非用户要求，不要运行 lifecycle script。
- 如果依赖元数据有变化，用 `npm install --package-lock-only --ignore-scripts` 刷新 `package-lock.json`。
- 如果需要重新生成 `packages/coding-agent/npm-shrinkwrap.json`，运行 `node scripts/generate-coding-agent-shrinkwrap.mjs`（用 `--check` 或 `npm run check` 验证）。带 lifecycle script 的新依赖需要经过评审，并在该脚本中显式加入 allowlist；绝不能悄悄添加。
- pre-commit 会阻止 lockfile 提交，除非设置了 `PI_ALLOW_LOCKFILE_CHANGE=1`。除非用户确实想提交 lockfile 变更，否则不要绕过。

## Git

这个 cwd 里可能同时运行着多个 pi session，各自修改不同的文件。Git 操作一旦碰到你自己改动之外的未暂存、已暂存或未跟踪文件，就会破坏其他 session 的工作。请遵守以下规则：

提交（commit）时：

- 只 commit 你在本次 session 中改过的文件。
- 用显式路径暂存（`git add <path1> <path2>`）；绝不用 `git add -A` / `git add .`。
- 提交前先运行 `git status`，确认暂存的只有你自己的文件。
- `packages/ai/src/models.generated.ts` 始终可以随你的文件一起提交。
- 提交信息格式：`{feat,fix,docs}[(ai,tui,agent,coding-agent)]: <commit message>`（可选多行）。信息要有信息量且简洁。

永远不要运行以下命令（会破坏其他 agent 的工作或绕过检查）：

- `git reset --hard`、`git checkout .`、`git clean -fd`、`git stash`、`git add -A`、`git add .`、`git commit --no-verify`。

如果 rebase 出现冲突：

- 只在你修改过的文件里解决冲突。
- 如果冲突出现在你没有改过的文件里，中止操作并询问用户。
- 永远不要 force push。

## Issue 与 PR

贡献者门槛（自动关闭流程、`lgtm`/`lgtmi`、质量标准）见 `CONTRIBUTING.md`。

审查 PR 时：

- 除非用户明确要求，不要运行 `gh pr checkout`、`git switch`，也不要以其他方式把 worktree 切到 PR 分支。
- 用 `gh pr view`、`gh pr diff`、`gh api`，以及本地 `git show`/`git diff` 对比已 fetch 的 ref，来查看 PR 元数据、commit 和补丁，全程不切换分支。
- 如果需要 PR 中的文件内容，fetch/读取到临时文件，或使用 `git show <ref>:<path>`，同样不要切换分支。

创建 issue 时：

- 为受影响的包加上 `pkg:*` 标签（`pkg:agent`、`pkg:ai`、`pkg:coding-agent`、`pkg:tui`），有多个适用就都加。

发 issue/PR 评论时：

- 把评论写到临时文件，用 `gh issue/pr comment --body-file` 发布（绝不要用 `--body` 传多行 markdown）。
- 评论保持简洁、技术性，语气跟随用户。
- AI 发出的每条评论都要以发起 prompt 所指定的 AI 生成免责声明行结尾（例如 `This comment is AI-generated by `/wr``）。

通过 commit 关闭 issue 时：

- 在提交信息中包含 `fixes #<number>` 或 `closes #<number>`，这样合并时会自动关闭对应 issue。多个 issue 时，每个 issue 都要重复关键字（`closes #1, closes #2`）；共用一个关键字（`closes #1, #2`）只会关闭第一个。

## 变更日志

位置：`packages/*/CHANGELOG.md`（每个包一份）。

`## [Unreleased]` 下的章节：`### Breaking Changes`（需要迁移的 API 变更）、`### Added`、`### Changed`、`### Fixed`、`### Removed`。

规则：

- 所有新条目都放在 `## [Unreleased]` 下。先读完整个章节，再追加到已有的子章节里；绝不要重复创建子章节。
- 已发布版本的章节（如 `## [0.12.2]`）不可改动；永远不要修改它们。
- 在 `main` 之外的分支或 pull request 上工作时，不要创建 changelog 条目。

署名：

- 内部（来自 issue）：`Fixed foo bar ([#123](https://github.com/earendil-works/pi/issues/123))`
- 外部贡献：`Added feature X ([#456](https://github.com/earendil-works/pi/pull/456) by [@username](https://github.com/username))`
