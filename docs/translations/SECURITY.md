# 安全策略

本文档旨在帮助你理解 Pi 背后的安全理念，以及安全边界在哪里。

总体而言，Pi 是一个在本地运行的 coding agent，处于运行它的用户的安全边界之内。监控它的操作，或者把它限制在容器、虚拟机或其他 sandbox 方案中，是用户自己的责任。

Pi 将本地用户账户以及该账户可写的文件视为与 Pi 进程自身处于同一信任边界之内。如果攻击者能够修改用户主目录、workspace、shell 启动文件、环境或 Pi 配置下的文件，他们通常就能影响 Pi 或其他本地开发工具。依赖这种既有本地写权限的报告不算安全漏洞，除非它们能证明 Pi 本身授予了这种写权限，或跨越了操作系统的权限边界。

Pi 依赖用户安装可信的 extension、加载可信的 skill，并且只在可信的仓库中使用 pi。这是因为 `AGENTS.md` 之类的文件或注释中的指令可以被轻而易举地用来对 coding agent 做 prompt 注入，而且这一点无法防护。

## 报告漏洞

如果你认为自己在 pi 或本仓库的其他包中发现了安全漏洞，请通过以下任一方式私下报告：

- 发邮件到 `security@earendil.com`，或
- 通过本仓库的 GitHub Security Advisories 提交私密报告

请包含以下内容：

- 问题描述及其影响
- 复现步骤、概念验证（proof of concept）或相关日志
- 受影响的包、版本、commit 或配置
- 已知的缓解措施

安全敏感的报告请不要开公开 issue。我们会审查报告，并在适当时协调披露。

## 范围

已发布的包、命令行工具、API 和仓库代码中的安全问题都在范围内，earendil 运营的 `pi.dev` 基础设施同样在范围内。

## 范围之外

- 本地代码执行或 sandbox 行为（Pi coding agent 有意不提供 sandbox）
- 用户安装的 pi extension 或 skill 的行为
- 在不可信仓库中工作的风险
- 安装不可信的 extension、skill、包或工具带来的风险
- 不可信 MITM 代理造成的问题
- Pi 安装暴露在公共互联网上
- prompt 注入攻击
- 泄露的第三方/用户控制的凭据类 secret
- 需要具备在目标机器上创建、修改、删除或替换文件、目录、symlink、环境变量、shell 配置或其他用户控制的本地状态的能力的报告。这包括 `~/.pi`、`~/.pi/agent/models.json`、workspace 文件、`AGENTS.md`、skill、extension、extension 配置、dotfile，以及通过 NFS、漫游配置文件或 dotfile 管理器同步的文件，除非报告能证明 Pi 本身授予了该访问权限。
- 由故意削弱的用户配置导致的问题。
- 需要可信本地输入/配置才能对 pi coding agent 构成的资源/DOS 类问题。
- 关于恶意模型输出的报告。
- 把用户批准或用户发起的本地操作当作漏洞来报告。

## 给报告者的说明

最有价值的报告是展示当前可复现的安全边界绕过、并证实其影响的报告。只展示本地 agent 预期行为、prompt 注入，或恶意可信 extension/skill 的报告，在这个安全模型下不算安全漏洞。

例如，向可信的 Pi 配置文件写入恶意内容，导致 Pi 执行命令、加载攻击者控制的 tool、把凭据发送到攻击者控制的 endpoint，或以其他方式改变行为——这类报告属于范围之外。

可能的话，请附上确切受影响的路径、包版本或 commit SHA、配置，以及针对最新 release 或最新 `main` 的概念验证。依赖类报告请附上证据，证明随包发布的依赖确实受影响，且该问题可以通过 Pi 触达。泄露凭据类报告请附上证据，证明该凭据归 Earendil 所有，或可以访问 Earendil 运营的基础设施或服务。
